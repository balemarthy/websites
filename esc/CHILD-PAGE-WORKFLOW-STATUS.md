## Confirmed program-page template (locked in `page-factory-system.md`, also the weekend-session template)

Hero (3D, Tripo→GLB→WebGL, via the existing `DoubtCloudHero` component) → Workflow D (one scroll-scrubbed statement, sourced verbatim from the page's own "What's In It For You"/promise opening) → Workflow E content blocks in this order:

1. What's In It For You + "What We Promise" callout
2. **Early CTA** — `Button variant="outline"`
3. Program-specific mechanism blocks (reuse `StageDiagram` where it fits — see below)
4. Qualifying block (`ForYouList`: Who This Is Not For / For You If, full version, not the homepage teaser)
5. **Mid CTA** — `Button variant="outline"`
6. Testimonials/proof (`ProgramTestimonials`, placeholder for now, TODO-marked + dev banner) — before the final ask, never after
7. What You Walk Away With + no-guarantee callout
8. Format/Price
9. **Primary CTA** — `Button variant="primary"` (full orange fill + glow), benefit-forward copy tied to the page's own hook, not generic verb+noun

Three CTA touchpoints, escalating weight (outline → outline → primary). Don't regress to text-link CTAs.

**Component reuse discovery:** `DoubtCloudHero` already renders floating HTML labels in a ring around the 3D model via its `statements` prop — that prop can carry *any* short text, not just doubt-statements (Bytes to Sockets used it for PDU-layer labels). When ring/spiral text is baked directly into the GLB's geometry instead, pass `statements={[]}` and skip the HTML ring entirely — verified safe across two builds now (BLE In Weekend, LM75 Driver Architecture): the ring-position math only runs inside `.map()`, which never executes on an empty array.

**New (LM75, 2026-09-17): `DoubtCloudHero` may need a secondary overlay-line slot.** LM75's hero calls for a short line of live HTML project-context text next to the 3D canvas (not baked into the mesh) — check the component's actual prop signature before assuming this exists; if it doesn't, this is the first page needing that addition, and it should be added following the component's existing conventions rather than inventing a new one-off element. Flagged as open in the LM75 build prompt, not yet confirmed built.

**Asset naming/path convention for a new hero:**
- `esc/public/models/<page-slug>-hero.glb`
- `esc/public/images/hero/<page-slug>-hero-bg.jpg` — **must be `.jpg`**, not `.png`. Match existing hero-bg dimensions: 1672×941 (16:9) — a higher-res 16:9 source (e.g. 2304×1296) is fine as-is.
- The background photo sits behind a transparent-alpha WebGL canvas via CSS (`--hero-bg-image`), with a dark-teal gradient (`--teal-600` → `--teal-800`) as fallback — so the photo itself needs to be in that same dark, moody tonal family (mostly dark teal, one sparing warm-orange accent point) or there's a visible mismatch/flash on load.
- Apply-page stub: `esc/app/apply/<page-slug>/page.tsx`, reusing the existing `ApplyForm` component — one prop change (`programLabel`, `qualifyingQuestion`), no new component. Log it in `BACKEND-TODO.md`.
- **New rule, learned the hard way on LM75 (2026-09-17): confirm the page's actual route slug BEFORE naming any hero asset.** Weekend-session routes/nav entries are sometimes pre-scaffolded as stubs ahead of content (check `app/weekend-sessions/<slug>/page.tsx` and the corresponding `Nav.tsx` href) under a slug decided earlier, possibly different from whatever name comes up naturally in brainstorming. LM75's assets were generated and named `lm75-in-a-weekend-*` during brainstorming, but the site's actual pre-existing route/nav slug was `lm75-driver-architecture` — caught only when checking the repo before writing the build prompt, requiring an on-device rename (`mv`, no data loss, but wasted a naming round-trip). Grep `Nav.tsx` and list `app/weekend-sessions/` for the target page's real slug before the first asset-naming conversation with Vamsi, not after assets exist.

**Hero-ring/spiral-text pattern, three variants now proven:**
1. **Live HTML ring** (Bytes to Sockets): flat labels via `DoubtCloudHero`'s `statements` prop, rendered in the live WebGL scene, not part of the GLB or the source photo.
2. **Baked-into-mesh, loose halo** (BLE In Weekend): ring text baked directly into the *source image* sent to Tripo, sculpted into extruded 3D typography as part of the GLB geometry, arranged as a halo at varying heights/distances around the object. `statements={[]}`, no HTML ring.
3. **Baked-into-mesh, disconnected ascending spiral** (LM75 Driver Architecture, 2026-09-17): six individual flat rectangular plaques, uniform size, no connecting structure between them or the central object (no rods, no rails, no staircase body) — each plaque floats independently, but their positions alone trace a continuous spiral climbing around the central IC, evenly spaced (gap ≈ one plaque's thickness), and each plaque is rotated on its own axis to face the camera regardless of its position in the spiral so all six read legibly in one frame. More literal/structured than BLE's loose halo — makes the "architectural ladder" concept physically concrete. `statements={[]}`, no HTML ring. Source image generated by Vamsi directly via ChatGPT this time (not OpenArt) — this session only supplied the prompts; Vamsi ran generation and the Tripo conversion himself end-to-end.

**Standing instruction from Vamsi, still in force:** when he asks for ring/spiral text to be baked into the image, do it — don't raise the known risk that Tripo's image-to-mesh conversion can mangle flat baked text into illegible geometry. He's aware and has explicitly overridden it.

Other notes still in force: trademark caution (use an original abstract glyph instead of a real protocol/standard's registered logo); when Vamsi asks a background to depict something concrete, bring the literal subject into frame blurred/atmospheric rather than defaulting to abstract mood-only imagery.

## Image generation workflow

- OpenArt MCP (`openart_generate_image`, model `gpt-image-2-5-sunburst`, `quality: "high"`) has been the default path for hero object photos feeding Tripo. **LM75 was the first page where Vamsi generated the source image himself via ChatGPT instead** and ran the Tripo conversion himself end-to-end — this session only supplied prompts, never touched the generation or conversion tools for this page. Always ask Vamsi which route he wants (OpenArt vs. doing it himself) before generating anything — don't assume OpenArt by default going forward now that both paths are proven.
- For a hero object + Tripo→GLB: prompt as a photorealistic studio product photo, plain white/transparent background, generous even margin, full deep focus (no bokeh) — Tripo needs a clean, geometrically legible silhouette. When ring/spiral text is meant to be baked into the mesh, the source photo needs the text composed into the frame as part of the brief (specific camera lens, angle, lighting setup, materials — written like a product photographer's brief), not just a plain object shot.
- For a hero *background* photo: the opposite brief — heavily out-of-focus/atmospheric, dark-teal-dominant, one sparing orange accent light, calm/low-contrast where the 3D object and text will sit, 16:9, matching the CSS fallback gradient tone, and depicting the page's actual subject concretely when Vamsi asks for that (e.g. LM75's background is a blurred macro shot of an actual I²C wire connection, not generic abstract mood).
- **Iteration is normal and can take several rounds.** LM75's hero concept went through multiple corrections before the final brief locked: fused-object sculpture → separate IC + thermometer → thermometer dropped entirely in favor of a "25°C" floating readout, and the spiral went from a vague "ladder" → an explicit spiral staircase → a disconnected-plaque spiral matching a reference image Vamsi provided. Each correction was a genuine refinement, not confusion — expect a real product concept to take several passes before the image brief is precise enough to generate correctly, and treat a shared reference image as authoritative geometry to match, not just inspiration.
- **Process lesson, still in force:** don't generate images (or take other irreversible/costly actions) without explicit go-ahead, even after providing a prompt on request. Provide the prompt, then ask before running the generation tool.
- **Network note:** `cdn.openart.ai` is not on the org's egress allowlist — direct `curl`/bash download of generated images fails (403). Downloading/converting generated assets goes through Vamsi himself or a browser tool, not a direct fetch.
- **File-transfer note:** for a large text file (e.g. a build prompt) with mixed UTF-8 (em-dash, rupee sign, typographic quotes, arrows), don't base64-encode it into a device_bash heredoc — this has corrupted transfers before. Use `SendUserFile` (from the cloud workspace) → `device_commit_files` (with the returned `file_uuid`, straight to the target device path) instead — clean, verified, no encoding step. Confirmed clean again on LM75's build prompt (189 lines, UTF-8 symbols intact, verified with `wc -l`/`grep` post-transfer). Same method used to push this status file itself into the repo.
